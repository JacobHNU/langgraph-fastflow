# GraphLoom 与 Workflow Studio 功能对照

分析日期：2026-10-26。

**结论**

手册中的 GraphLoom 已描述一个涵盖可视化编排、Python 工程生成、组件市场、多人协作及运行环境管理的平台。当前 Workflow Studio 已实现 FlowGram 画布、LangGraph 执行、多轮 Agent、版本发布和可追溯的业务执行闭环，但通用业务输入、自由模型任务和外部连接器仍明显不足。

建议继续完善当前项目，优先让用户能够不改后端源码就接入新业务。保留现有执行引擎、发布快照、证据和审批机制，补齐通用输入、节点提示词、模型配置引用、HTTP/数据库连接器以及 Skill/Tool 管理。暂不把 Python 代码与画布双向同步作为第一阶段目标。

**依据与判断口径**

- 对方依据为用户提供的《智能问答系统-用户使用手册_V1.0.pdf》，正文标题为《GraphLoom 用户使用手册》，共 24 页。下文页码为 PDF 页码，与页脚一致。
- 手册明确称产品处于内部测试阶段。本次未访问其内网服务，也未取得源码，不能验证性能、隔离强度或功能稳定性。
- 当前侧依据为 `code/` 内的实际后端、前端代码及已有验收记录，包含证据编号、回收站、对话编排和在线模型超时修复。不是只按最初设计指南判断。
- “部分具备”表示存在相关执行基础，但用户可配置范围或完整使用流程尚未对等；“未说明”表示手册不足以判断，不能直接认定对方没有。
- 本次是功能分析，没有重新运行全套测试，也没有修改业务实现。

**二、画布、状态与模型能力对照**

| 能力 | GraphLoom 手册 | 当前实际实现 | 判断 |
| --- | --- | --- | --- |
| 基础画布 | 添加、拖动、连线、属性面板、撤销重做、布局 | FlowGram 官方画布，已有对应能力，支持面板调节尺寸 | 已具备基础能力 |
| 工作流管理 | 工作区新建、打开、改名、删除与共享 | 新建、复制、搜索、改名、描述、软删除、恢复、并发版本检查 | 已具备单工作空间管理；缺少团队共享 |
| 通用入口 | 用户输入进入 messages，可配置其他 State 字段 | `ProjectInput` 固定为 project_id、progress、task 等字段，拒绝额外字段 | 缺少通用输入 Schema 和动态表单 |
| State 编辑 | 用户定义类型和 reducer | 固定 inputs/results/final，节点通过显式引用取值；可配置参数名与字段路径 | 部分具备数据传递，缺少 State 类型/reducer 编辑 |
| 模型连接 | 保存多个厂商，节点选择；支持个人覆盖 | 可视化服务商、地址、模型、Key、超时、Token、Temperature；当前只有一份活动配置 | 全局配置可用，缺少多配置档案及节点选择 |
| 单次 LLM | 节点自由提示词、厂商、Token、超时 | 有 direct_model，系统提示固定为受限项目分析，输出依赖 summary/risk_level/recommendations | 具备调用基础，尚非通用 LLM 节点 |
| ReAct | 自主选择目录中的工具与技能，最大轮次 1–50 | 真正使用 LangChain create_agent；有预算、上下文和只读项目查询工具 | 多轮基础已具备，工具与任务范围较窄 |
| Deep Agents | 手册未明确说明接入 Deep Agents | 真正使用 create_deep_agent、StateBackend、绑定 Skill 和受限文件工具 | 当前已明确实现；不推断对方内部实现 |
| 条件路由 | 分类标签配合 predicate，支持多个分支 key | condition 运算符配合 true/false 两个分支，不能在面板定义多路标签 | 部分具备，缺少分类节点与多路路由 |
| 画布循环 | 有独立循环节点、内部子画布、最大轮次及退出条件 | 编译器拒绝循环图；Agent 内部可多轮，但不是工作流循环 | 缺少有界循环节点 |
| 子流程复用 | 引用其他工作区，双击进入，生成时同步模块副本和状态 | managed_agent/subworkflow 固定引用发布版本，记录父子运行并取权限交集 | 已有固定版本复用，缺少嵌套画布体验 |
| 子流程分组框 | 对外发布时合为一张步骤卡，内部轨迹仍可查看 | 未实现相应分组与发布展示 | 缺少展示层分组 |
| 人工介入 | 按钮选项、文字反馈、写回指定 State 字段 | 有 approve/reject 和 LangGraph interrupt/resume，绑定方案摘要、有效期和写操作 | 具备受控审批，缺少通用人工输入表单 |
| 最终输出 | 模板插入任意 State 字段生成回复 | 映射输出结构化结果，显示项目或分析结果；输出前必须经过 verify | 缺少通用模板回复和自定义结果展示 |

重要区别：当前对话编排助手生成的是受现有注册表和校验器约束的候选流程。它能降低编排操作成本，但不能凭空提供尚未实现的 HTTP、SQL、MCP 或循环执行器。

通用化也不能只改输入面板：入口 `ProjectInput`、固定系统提示词、授权对象白名单和 `verify` 的业务检查都围绕项目场景实现，需要一起参数化，并保留明确的服务端授权与核验边界。

**三、集成、组件与开发体验对照**

| 能力 | GraphLoom 手册 | 当前实际实现 | 判断 |
| --- | --- | --- | --- |
| HTTP API | 有独立 HTTP 节点及低代码参数面板 | 业务调用集中于固定注册函数与本地项目适配器 | 缺少通用连接器，优先补齐 |
| MySQL | 参数化查询，结果写入 rows | 无 SQL 连接、查询节点或相应配置接口 | 缺失 |
| Neo4j | Bolt/Cypher 查询，结果写入 records | 无图数据库连接与查询节点 | 缺失；是否需要取决于业务数据源 |
| 自定义 Python | 在界面或 VS Code 编写 run(state) | python/python_workflow 只调用已注册函数，不执行画布内任意源码 | 部分基础相关，但不等同于自定义代码节点 |
| 外部程序 | 命令模板、stdout/stderr、单独试跑 | 没有 exe、脚本或命令行执行节点 | 缺失 |
| MCP | 远程工具清单发现、参数导入、鉴权、试跑；部分本地回退 | 无 MCP 客户端、目录或工具发现界面 | 缺失 |
| 工具管理 | Python/程序/MCP 三类工具可配置、测试、分类、启停、共享 | `FUNCTIONS` 固定注册；Agent 仅开放项目只读查询 | 缺少面向用户的工具管理 |
| Skill 管理 | 方法论表单、预览、新建、编辑、复制、共享、启停 | 已加载文件 Skill，界面只读，发布绑定版本和 SHA | 执行与绑定具备，管理能力缺失 |
| 工程生成 | 生成 LangGraph Python 工程与 requirements、部署说明 | Pydantic DSL 在后端编译成 StateGraph，不生成每个工作流的 Python 工程 | 实现路线不同；独立工程交付能力缺失 |
| 导入导出 | 工程及依赖声明导出；部分结构代码可解析回画布 | 流程 JSON 导入导出 | 部分具备，不能把 JSON 导出当作独立部署包 |
| 双向代码同步 | 属性更新代码、代码常量回写属性、静态图结构解析、USER CODE 保护 | 无浏览器代码编辑器、AST 逆向解析或 VS Code 工作区同步 | 缺失，建设成本高 |
| 依赖管理 | 离线 wheel 上传、检查安装、组 venv | 项目级 uv/npm 锁文件和安装脚本 | 缺少用户侧依赖池和运行环境管理 |

当前的主要集成差距不是“能否执行 Python”，而是新增一个客户查询、订单接口或报表分析任务时，是否仍需开发者修改后端源码。现在通常需要；GraphLoom 手册描述的多种节点和 SkillHub 尝试把这些工作交给使用者配置。

当前这些保障主要围绕两个测试项目和本地业务适配器实现。不能把它们直接等同为已完成任意业务系统的生产审计或事务保障。

**五、四个容易误判的地方**

1. **Agent 多轮不等于画布循环。** Agent 的工具选择循环发生在一个节点内部；有界循环节点可以反复执行包含多个不同节点、甚至人工输入的子流程。当前只具备前者。
2. **Neo4j“知识库”不等于完整 RAG。** 手册展示的是图数据库查询，没有据此证明存在文档上传、切块、Embedding、向量检索、重排和引用溯源。当前也没有完整 RAG；不应因标题而扩大对方能力范围。
3. **静态依赖安装不等于代码沙箱。** 手册中的组 venv 用于依赖隔离，不足以证明能隔离文件、网络或进程权限。当前未开放任意代码，若新增代码/程序节点，需要另行设计运行隔离。
4. **不要混淆外部模型平台和编排软件。** 第 3–4 页统一模型平台的 Token 配额、余额和历史对话说明，不能直接算作 GraphLoom 自身的计费功能或运行历史限制。

另需注意地址语义：手册示例要求填写 `/chat/completions`，当前使用 ChatOpenAI 的 Base URL，SDK 会补全相应请求路径。迁移连接配置时应适配地址，不能机械复制最终接口路径。

**六、继续开发的建议顺序**

以下是功能依赖顺序，不是工期估算。若近期要让多人共同使用，身份、对象归属和权限隔离应作为第一阶段前置条件。

| 阶段 | 建议范围 | 必要性及验收方式 |
| --- | --- | --- |
| 第一阶段：通用业务闭环 | 通用输入/输出 Schema 与动态表单；节点提示词、输出 Schema；多个模型连接档案及节点引用；HTTP 连接器和受控凭据引用；基础数据转换、可配置业务核验器 | 最优先。用户只通过界面搭建“输入客户编号 → HTTP 查询订单 → LLM 总结 → 人工确认 → 输出”，不修改后端源码；沿用快照、证据和运行日志 |
| 第二阶段：能力管理 | Skill 编辑/版本；Tool 注册、参数 Schema、单工具试跑、启停；MCP 工具发现；按实际场景增加只读 SQL 或 Neo4j | 使新业务能力不再依赖固定注册表。新增一个工具后能被节点和 Agent 选择，停用/升级后引用检查和历史版本行为清楚 |
| 第三阶段：复杂流程 | 多路条件、有界循环、循环退出与次数预算、通用人工反馈、子流程导航；确有并行需求时再设计 reducer | 支持“生成 → 检查/人工反馈 → 最多重试三次 → 输出”。先建立循环子图协议，再改变当前仅支持 DAG 的校验和执行假设 |
| 第四阶段：团队与交付深化 | 完善组/角色、共享、审批人、配额；按部署需求建设环境隔离、离线依赖池、独立运行包 | 团队和内网交付时必要，避免把项目级 .venv 当作每工作流隔离 |
| 后续可选：专业代码工作台 | 代码编辑器、Git/IDE 联动、Python 工程生成与有限逆向解析 | 仅在用户确需编写复杂节点或交付源码工程时投入；不应为追求表面功能一致而先重写现有编译路线 |

架构上保留一份规范化、版本化的 DSL 作为事实来源。参数表单、对话提案和可选代码生成都应落到该协议；不要在尚未有通用执行能力时，同时引入 YAML、Python、画布三套可互相覆盖的主定义。

新连接器和工具继续经过当前统一执行边界，记录输入、响应、证据和错误。流程引用凭据 ID，由后端解析凭据，不把密钥写入节点定义、生成代码或导出包。

不建议第一阶段完整照搬 USER CODE 模板保护、任意 Python 到画布的逆向解析或离线 wheel 市场。这些功能需要维护较复杂的同步与运行环境合同，对“先把真实业务流程配置出来”的帮助不如输入、提示词和连接器直接。

**七、两个具体场景**

**客户服务查询。** 输入客户编号，调用订单 HTTP API，按状态多路分流，用 LLM 整理回复，再由人工补充意见。GraphLoom 手册已有这些组成能力；当前除了两个内置项目，缺少通用输入、HTTP、自由提示词、多路分支和文字反馈，需要上述第一阶段及部分第三阶段能力。

**有审批的项目更新。** 查询项目状态，生成修改方案，人工批准，写入并读回，再查看证据。当前已在本地测试适配器实现完整示例；GraphLoom 能通过代码、HTTP 和人工节点组合类似流程，但手册没有足够信息证明自带同等的幂等、摘要审批、对象版本和独立评估机制。

因此，若目标是通用低代码 Agent 平台，应明显扩展当前产品面；若目标是可追溯的企业业务自动化，应吸收对方的连接器和组件管理体验，同时保留并推广当前执行治理能力。
